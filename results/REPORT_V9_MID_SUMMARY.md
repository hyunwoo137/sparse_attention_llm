## 0. 한 문단 요약

`tail`은 통계적 의미의 tail이 아닙니다. 30,427개 토큰의 **유효 개수(participation
ratio)가 3.65**이고 **단일 토큰 하나가 tail 질량의 51.8%**를 가집니다. 이 구조에서는
평균 value 프록시 `v̄_b`의 *방향*이 이미 틀려 있으므로, 질량 `S_b`만 고쳐도 오차는
줄지 않고 **늘어납니다** — 완벽한 질량을 줬을 때 상대오차가 0.2175 → **0.3508**로
악화됩니다(§3.2). 이것이 CovUTA·j1·j2·"정확한 S_T" 계열이 전부 실패한 단일 원인이며,
동시에 RetroInfer·ClusterKV·CentroidKV·Double-P가 공유하는 **centroid 프록시의 구조적
상한**입니다. 우리 방법(expand)은 프록시를 개선하는 대신 문제 bin을 **프록시 집합에서
제거**하므로 그 상한에 묶이지 않습니다. 조준에 쓰는 통계 `û_b = z̄_b + c·σ_b`는 2차
모멘트 기반 UCB이며, 기존 방법이 공통으로 쓰는 1차 모멘트 랭킹 `z̄_b + log n_b` 대비
**가장 무거운 tail 토큰의 회수율을 0.325 → 0.643으로 2배** 올립니다(§4.3).

## 2. 현재 방법 (확정본)

```
1. sink + local + HAT top-k 로 heavy hitter 선택               -> S,  |S| = ρN
2. 나머지(tail)를 인접 인덱스 32토큰 런으로 분할                -> B개 bin
3. 캐시된 key-side 통계로 bin 모멘트   (query 무관, 캐싱 가능)
     z̄_b   = s · q · k̄_b
     σ_b²  = s² · Σ_d q_d² · Var_b(k_d)                        -> bin당 O(d)
4. 랭킹   û_b = z̄_b + c·σ_b,   c = 3                          -> 상위 m=8 bin
5. 상위 m bin을 프록시 집합에서 빼고 그 토큰들을 정확히 계산    -> |E| = 256
6. 하나의 online softmax로 합성:
     out = ( Σ_{i∈S∪E} e^{z_i} v_i + Σ_{b∉top-m} e^{ℓ_b} v̄_b )
         / ( Σ_{i∈S∪E} e^{z_i}     + Σ_{b∉top-m} e^{ℓ_b}     ),   ℓ_b = z̄_b + log n_b
```

`kappa_mode="none"` — Jensen 보정은 쓰지 않습니다(§3이 이유를 설명합니다).
전 과정에 **순환이 없습니다**: bin 멤버십은 위치만으로 결정되고, `k̄_b`·`Var_b(k)`는
query 무관하며, 참 로짓은 확장된 256개 토큰에 대해서만 계산합니다.

## 3. 【신규】 softmax 분모/분자 분해 — 왜 "보정"이 아니라 "조준"인가

`run_softmax_decomp_diag.py`, 15,360행 (32 layer × 32 head × 2 subset × qrow),
density 5%, HAT 셀렉터. dense 출력을 반환하므로 생성 궤적은 교란되지 않습니다.
원자료 `results_v9_decomp/decomp_5pct_hat.parquet`.

### 3.1 정확한 2항 분해

이 문헌의 **모든** tail 추정기 — 우리 것, vAttention, RetroInfer, ClusterKV,
CentroidKV, Double-P — 는 결국 (질량, 방향) 쌍 `(Ŝ, μ̂)`을 heavy 집합과 한 softmax로
합치는 것입니다:

$$\hat o = \frac{\text{num}_H + \hat S\,\hat\mu}{S_H + \hat S}$$

`w = S_T/(S_H+S_T)`, `ŵ = Ŝ/(S_H+Ŝ)`로 두면 출력 오차가 **근사 없이** 두 항으로
갈라집니다:

$$\boxed{\;\hat o - o \;=\; \underbrace{(\hat w - w)\,(\mu_T - \mu_H)}_{\textbf{A: 분모/질량}} \;+\; \underbrace{\hat w\,(\hat\mu - \mu_T)}_{\textbf{B: 분자/방향}}\;}$$

**항등식 검증:** 116개 추정기 전체에서 `(ô − o) − (A + B)`의 중앙 노름이 최대
**6.6e-08** (fp32 한계). 이 분해는 가정이 아니라 항등식입니다.

### 3.2 Q1 — "분자는 고칠 필요 없다"는 V1의 결론은 **측정 인공물**이었습니다

| 추정기 | 상대오차 | **A (질량)** | **B (방향)** | ŵ |
|---|---|---|---|---|
| UTA (단일 프록시) | 0.21745 | 0.22094 | **0.00932** | 0.00440 |
| UTA + j1 (`σ²/2`) | 0.26117 | 0.10190 | 0.20500 | 0.10347 |
| UTA + j2 (`log(1+σ²/2)`) | 0.19482 | 0.19058 | 0.03852 | 0.01857 |
| **oracleS** (정확한 `S_T` + `v̄_T`) | **0.35084** | **0.00000** | **0.35084** | 0.19536 |
| oracleμ (UTA 질량 + 정확한 `μ_T`) | 0.22094 | 0.22094 | 0.00000 | 0.00440 |
| multibin b32 | 0.18804 | 0.18706 | 0.03766 | 0.01934 |
| multibin b32 + j2 | 0.17771 | 0.15099 | 0.07294 | 0.03696 |
| expand m1 (c3) | 0.11162 | 0.06428 | 0.05463 | 0.11146 |

참 tail 가중 `w = 0.19536`인데 **UTA의 `ŵ = 0.00440` — 44배 과소추정**입니다.
B항은 `ŵ`가 곱해지므로, `ŵ≈0`인 동안에는 방향이 아무리 틀려도 오차에 나타나지
않습니다. 그래서 V1이 "정확한 `μ_T`를 줘도 변화가 없다"를 관측한 것이며, 그것은
**분자가 정확하다는 증거가 아니라 분자가 가려져 있다는 증거**였습니다.

**질량을 고치는 순간 방향 오차가 드러납니다: B가 0.00932 → 0.35084 (37.6배).**
결과적으로 **완벽한 분모 보정은 무보정보다 61% 나쁩니다** (0.3508 vs 0.2175).

> **따라서: 분모만 건드리는 모든 추정기는 `‖w(v̄_T − μ_T)‖/‖o‖ = 0.351`이라는 하한에
> 걸립니다.** Jensen이든, moment expansion이든, top-p 임계든, 더 정확한 centroid든
> 무관합니다. 이 하한이 UTA 자신의 오차(0.2175)보다 크다는 것이 핵심입니다.

### 3.3 왜 그런가 — tail은 통계적 tail이 아닙니다

| 지표 | 중앙값 |
|---|---|
| tail 토큰 수 `n_T` | 30,427 |
| tail이 가진 attention 질량 `w` | 0.19536 |
| **participation ratio** `(Σe)²/Σe²` | **3.65** |
| PR / n_T | 0.00012 |
| **최상위 1개 토큰의 tail 질량 점유율** | **51.8%** |
| 최상위 8개 토큰의 점유율 | 59.6% |
| headroom (`z_max,tail − z̄`) | 13.28 nats (≈ 59만 배) |
| tail 로짓 분산 `σ²` | 5.578 |

30,427개 토큰의 **유효 개수가 3.65개**이고, **한 토큰이 tail 질량의 절반**을 가집니다.
그러므로 참 tail 방향 `μ_T`는 사실상 **그 한 토큰의 value 벡터**입니다. 평균
`v̄_b`는 그것을 31개에 희석한 값이므로 **방향 자체가 다릅니다.**

이것이 "질량만 고치면 더 나빠지는" 정확한 기전입니다:

- 보정 전: `ŵ≈0` → 출력 ≈ `μ_H`. 오차 = `w‖μ_H − v_j‖`
- 완벽 보정: `ŵ=w` → 출력에 `v̄_b`가 `w`만큼 들어감. 오차 = `w‖v̄_b − v_j‖`

고차원에서 무작위 벡터는 거의 직교하므로 `‖v̄_b − v_j‖ ≈ ‖μ_H − v_j‖`이고,
**보정의 기댓값 이득은 0**입니다. 측정값은 그보다 나빠서(0.351 > 0.218), `v̄_b`가
`μ_H`보다 오히려 `v_j`에서 더 멀다는 뜻입니다 — `μ_H`는 실제 attention 가중 평균이라
문맥과 정렬돼 있는 반면 `v̄_b`는 임의의 31개 토큰의 산술 평균이기 때문입니다.

**확장(expand)은 두 항을 동시에 무너뜨립니다.** bin을 프록시 집합에서 빼면 `v_j`가
정확히 들어가므로 A와 B가 함께 줄어듭니다 — m=8에서 A 0.221→0.043, B는 0.351(가려짐이
풀린 값) 대비 0.055. 이것이 보정과 조준의 구조적 차이입니다.

## 4. 【신규】 ICLR 포지셔닝 — 무엇이 novelty이고 어떻게 주장할 것인가

### 4.1 경쟁 방법의 실제 구조 (원문 확인)

| 방법 | 분할 | 프록시 랭킹 통계 | 미선택 구간 처리 | 예산 결정 |
|---|---|---|---|---|
| **RetroInfer** (VLDB'26) | spherical k-means (segmented) | `q·C_i` — **centroid 내적, 1차 모멘트** | estimation zone: `ã_i = e^{q·C_i}/Z`, value는 `VS_i`(cluster value 합) | **고정** r (민감도 분석으로 선택) |
| **ClusterKV** | k-means (semantic) | centroid 내적 | recall 안 된 cluster는 미기여 | 고정 top-c |
| **CentroidKV** | Chunked Soft Matching 병합 | — (압축 표현) | degree 로그 가중으로 전부 기여 | 압축률 r 스케줄 |
| **Double-P** (2026) | cluster centroid | **size-weighted centroid logit** `n_c·e^{z̄_c}` (eq.5) | 공유 정규화로 근사 기여 (eq.8/9) | **top-p 임계 p₁, p₂ (adaptive)** |
| **vAttention** | — (랜덤 샘플링) | — | 샘플 기반 불편 추정 + adaptive budget | ε, δ 기반 |
| **본 연구** | **인접 32토큰 런** (분할 비용 0) | **`z̄_b + c·σ_b` — 2차 모멘트 UCB** | 동일 softmax 병합 `ℓ_b = z̄_b + log n_b` | 고정 m / **per-head 정적 (§5.3)** |

RetroInfer 원문의 "accuracy-bounded attention estimation"은 **Jensen 부등식의 한쪽
방향**입니다: `e^{q·C_i} ≤ (Σ_j e^{q·K_j})/s_i` (eq.3). 즉 **자신이 항상 과소추정임을
명시적으로 인정**하고 그 사실을 "bound"라고 부릅니다. 우리가 측정한 Jensen 갭
`K₁ ≈ 3.7 nats`가 그 과소추정의 크기이고(V4 §1), §3.2는 그것을 고치는 것이 왜
해결책이 아닌지를 보입니다.

RetroInfer는 또한 이렇게 씁니다: *"Due to the high variety of sparsity ratios across
model layers, attention heads, queries, and task types, determining the optimal number
of clusters for the retrieval zone is challenging, if not unattainable."* — 이는 §5가
정면으로 다루는 열린 문제입니다.

### 4.2 우리가 다른 지점 — 4개의 축

#### (N1) 문제의 재정의: 오차는 **질량**이 아니라 **방향**에 있다 [이론 + 측정]

§3의 2항 분해와 그 측정이 이 문헌의 암묵적 전제를 반증합니다. 모든 centroid 방법은
"centroid 추정의 정확도를 높이면 좋아진다"를 전제하는데, 완벽한 질량이 **오차를
61% 악화**시킵니다. **이 관측 자체가 독립적 기여**입니다 — 이후 어떤 방법을 쓰든
"centroid 추정 정밀도"는 최적화 대상이 아님을 보이기 때문입니다.

주장 문장: *"We show that the softmax error of any centroid-proxy attention estimator
decomposes exactly into a mass term and a direction term, that the mass term masks the
direction term, and that improving the mass estimate is therefore not merely
insufficient but actively harmful."*

#### (N2) centroid 프록시의 **정보 상한**을 계산해서 보였다 [측정]

"완벽한 클러스터별 질량 + 평균 value"는 어떤 centroid 방법도 넘을 수 없는 하한입니다.
분할 방식별로 측정했습니다 (상대 출력오차 중앙값):

| 분할 (프록시 집합) | 완벽한 질량 하에서의 하한 | 비고 |
|---|---|---|
| 인접 32토큰 (951 bin) | **0.36144** | 우리 분할 |
| **spherical k-means, 1024 cluster** | **0.08494** | **RetroInfer / ClusterKV류** |
| ↳ 같은 클러스터 + 배포 가능한 질량 추정 | 0.11901 | **RetroInfer 추정기 그 자체** |
| 참 로짓 등간격 16 bin | 0.00598 | 도달 불가 (full QK 필요) |
| 참 로짓 등간격 64 / 256 bin | 0.00098 / 0.00019 | 동일 |

읽는 법: 분할이 **query별 로짓 순서와 정렬되면** centroid 프록시는 거의 완벽합니다
(0.0002). 하지만 k-means는 **query 무관**으로 만들어지므로 그 정렬을 얻을 수 없고,
adjacency(0.361)와 이상적 정렬(0.006) 사이의 60배 격차 중 **4.3배만 회수**합니다.
**즉 centroid 방법의 성능은 클러스터 품질이 아니라 "key 유사도가 로짓 순서를 얼마나
대리하는가"에 의해 상한이 정해지고, 그 대리는 부분적입니다.**

우리 방법은 프록시를 개선하는 것이 아니라 **프록시 집합에서 제거**하므로 이 하한에
묶이지 않습니다: 인접 32토큰이라는 **가장 나쁜 분할** 위에서도 expand m8이 0.08539로
k-means 1024의 완벽-질량 하한(0.08494)과 동률이고, m16(0.07757)·m32(0.06747)는 그
하한 **아래로 내려갑니다.** 같은 통계를 k-means 분할에 얹으면(§4.2 N3) m8에서
0.06691로 하한을 크게 밑돕니다. 프록시를 아무리 잘 만들어도 도달할 수 없는 값에,
프록시를 8개 빼는 것으로 도달한다는 것이 요점입니다.

#### (N3) 랭킹 통계의 교체: 1차 모멘트 → **2차 모멘트 UCB** [방법, 이식 가능]

**이것이 가장 직접적인 차별점이며, 경쟁 방법의 분할 위에서도 성립합니다.**

동일 분할·동일 토큰 예산에서 랭킹 통계만 바꾼 결과 (상대 출력오차 중앙값):

| 분할 + 랭킹 | m=1 | m=2 | m=4 | m=8 | m=16 | m=32 |
|---|---|---|---|---|---|---|
| k-means 1024 + **mass** `z̄+log n` *(= RetroInfer / Double-P)* | 0.09883 | 0.09587 | 0.09127 | 0.08437 | 0.07486 | 0.06261 |
| k-means 1024 + **`z̄ + 3σ`** *(우리 통계, 그들 분할)* | **0.08167** | **0.07772** | **0.07329** | **0.06691** | **0.05951** | **0.04992** |
| adjacency 32 + mass | 0.15473 | 0.13642 | 0.12157 | 0.10665 | 0.09207 | 0.07628 |
| adjacency 32 + **`z̄ + 3σ`** *(본 연구)* | 0.11162 | 0.09846 | 0.09192 | 0.08539 | 0.07757 | 0.06747 |

(읽은 토큰 수는 m별로 정합: k-means m=8에서 mass 276 vs c3 271토큰.)

**UCB 랭킹은 어떤 분할 위에서도 −17 ~ −28% 오차를 줍니다.** k-means 위에서 −20.7%
(m=8), adjacency 위에서 −19.9% (m=8). **즉 이것은 RetroInfer/Double-P의 대체재가
아니라 그들에 대한 drop-in 개선입니다** — 논문에서 그렇게 주장하는 편이 강합니다.

기전은 회수율에서 직접 보입니다 — **가장 무거운 tail 토큰이 든 bin을 뽑았는가**:

| 랭킹 규칙 | m=1 | m=2 | m=4 | m=8 | m=16 | m=32 |
|---|---|---|---|---|---|---|
| `mass` = `z̄_b + log n_b` (1차 모멘트) | 0.325 | 0.470 | 0.569 | 0.651 | 0.725 | 0.787 |
| `massj2` = 위 + `log(1+σ²/2)` | 0.442 | 0.578 | 0.664 | 0.731 | 0.787 | 0.835 |
| `z̄_b` 단독 (c=0) | 0.353 | 0.532 | 0.633 | 0.704 | 0.769 | 0.822 |
| `z̄_b + 1σ_b` | 0.464 | 0.650 | 0.731 | 0.784 | 0.831 | 0.867 |
| `z̄_b + 2σ_b` | 0.564 | 0.722 | 0.786 | 0.828 | 0.863 | 0.895 |
| **`z̄_b + 3σ_b`** (채택) | **0.643** | **0.768** | **0.817** | **0.854** | **0.882** | **0.909** |
| `z̄_b + 4σ_b` | 0.698 | 0.794 | 0.835 | 0.866 | 0.894 | 0.919 |
| `z̄_b + σ_b√(2 log n_b)` (이론값) | 0.629 | 0.744 | 0.797 | 0.837 | 0.871 | 0.901 |
| 랜덤 (대조군) | 0.0001 | 0.0001 | 0.0003 | 0.0022 | 0.0205 | 0.0293 |

**m=1에서 회수율 0.325 → 0.643, 정확히 2배입니다.** 이유는 §3.3의 구조입니다:
13 nats 튄 토큰 하나가 31개 평범한 토큰과 같은 bin에 있으면 **그 bin의 평균은
평범합니다.** 1차 모멘트 랭킹은 그 bin을 중위권에 놓고, `σ_b`는 정확히 그것을
탐지합니다. `σ_b²`가 "얼마나 튀었는지"를 정량화하는 데는 무효였지만(§3.2),
"뭔가 튀었다"를 탐지하는 데는 유효했던 것입니다.

**`c`의 이론적 근거:** bin 내 로짓이 sub-Gaussian이면
`max_i z_i ≲ z̄_b + σ_b√(2 log n_b)`이므로 `c`는 `√(2 log n_b)`의 역할입니다.
`n_b=32`에서 2.63, `n_b=64`에서 2.88 — 손으로 고른 `c=3`이 이 값입니다. 실제로
`ucbln` 행이 `c≈2.8` 위치에 정확히 놓입니다. 즉 c는 하이퍼파라미터가 아니라
bin 크기의 함수로 유도됩니다.

#### (N4) 분할을 **위치 인접성**으로 고정한 것이 시스템 이점을 낳는다 [시스템]

k-means 분할은 정확도에서 앞서지만(0.085 vs 0.361 하한) 대가가 있습니다:

| | k-means 클러스터 | 인접 32토큰 런 |
|---|---|---|
| 구축 비용 | prefill에서 Lloyd 반복 | **0** (위치만으로 결정) |
| 증분 갱신 | 재클러스터링 필요 | **마지막 bin만 갱신** |
| 확장 시 메모리 접근 | 흩어진 토큰 gather (행 256 B) | **연속 8 KB 블록** |
| 측정된 gather 대역폭 | 766 GB/s (V7 §2.4, blk=1) | **2,476 GB/s** (V7 §3.1, blk=32) |
| 커널 | 토큰 단위 간접 참조 | fused Triton, B=32에서 **dense의 0.53×** |

**V7 §2.4가 규명한 것은 "흩어져서 느린 게 아니라 행이 256바이트라 간접 참조가
상각되지 않아서 느리다"였습니다.** 인접 분할은 순환을 피하려고 고른 것인데, 그
선택이 정확히 이 문제를 없앱니다. k-means 클러스터는 정의상 이 성질이 없습니다.

정직한 서술: **정확도는 k-means가 유리하고, wall-clock은 인접이 유리하며, 랭킹
통계(N3)는 둘 다에 적용됩니다.**

### 4.3 논문 주장 구조 (제안)

**제목 방향:** *Aim, Don't Correct: Second-Moment Routing for the Approximated Tail
of Sparse Attention*

1. **관측** — sparse attention의 tail은 통계적 tail이 아니다. 유효 토큰 3.65개,
   최상위 1개가 질량의 52%. (§3.3)
2. **정리(분해)** — 임의의 `(Ŝ, μ̂)` 추정기에서 오차 = A(질량) + B(방향), 항등식.
   `ŵ→0`이 B를 가린다. (§3.1)
3. **따름정리(불가능성)** — 분모만 개선하는 어떤 추정기도 `‖w(v̄_T − μ_T)‖`에 걸리며,
   이 값은 무보정 오차보다 크다. **분모 정밀도 개선은 해롭다.** (§3.2)
4. **하한 측정** — centroid 프록시의 하한을 분할별로 계산. k-means 1024에서 0.0849.
   (§4.2 N2)
5. **방법** — 2차 모멘트 UCB `z̄_b + σ_b√(2 log n_b)`로 bin을 **라우팅**하고,
   선택된 bin은 프록시에서 제거해 정확히 계산. (§2)
6. **결과** — RULER 32K에서 동일 예산 기준 vAttention +16.56%p, HAT +13.71%p,
   UTA +4.01%p; density 3%에서 격차 최대(+9.79%p). fused 커널로 B≥8에서 dense보다
   빠름. (§1)
7. **이식성** — 같은 통계를 k-means 분할에 얹으면 −20.7%. 기존 시스템에 대한
   drop-in. (§4.2 N3)
8. **예산 배분** — per-head 정적 배분이 동일 예산에서 −8.3% RMSE, 런타임 비용 0.
   per-row adaptive는 +49% latency에 이득 없음. (§5)

## 5. 【신규】 Adaptive budget — 수학적 모델, 측정된 헤드룸, latency

### 5.1 모델

bin `b`를 프록시로 남길 때 발생하는 출력 오차는 §3.1에 의해 그 bin의 분모 점유율로
상계됩니다:

$$\varepsilon_b \;\le\; \frac{S_b}{S_H + S_T}\,\bigl\|\bar v_b - \mu_b\bigr\| \;\le\; 2V\cdot\frac{S_b}{D}$$

`S_b`는 모르지만 §4.2 N3의 UCB가 상계를 줍니다 — bin이 지배 토큰 하나로 이루어진
최악의 경우 `S_b ≲ exp(z̄_b + c·σ_b) =: M̂_b`. 총예산 제약 하에 총오차를 최소화하는
문제는 water-filling이고, 그 정상조건은 **행별 목표가 아니라 한계값에 대한 단일
전역 임계**입니다:

$$\text{expand } b \iff \frac{\hat M_b}{\hat D_{\text{row}}} > \theta$$

대안으로 행별 목표(잔여 위험 `R(m) = Σ_{b\notin E} \hat M_b/\hat D ≤ τ`)를 쓸 수
있고, 이는 정렬 + cumsum + searchsorted입니다. **두 규칙 모두 랭킹이 이미 계산한
`z̄_b`, `σ_b` 외에 새 데이터 이동을 요구하지 않습니다.**

| water-filling (j2 질량) θ=3e-4 | 0.08906 | 0.12728 | 25.11 | p50 15, p99 64 |
| 행별 상대 규칙 γ=0.3 | 0.09564 | 0.13877 | 4.76 | p50 2, p99 46 |
| 행별 상대 규칙 γ=0.1 | 0.08235 | 0.12142 | 17.13 | p50 4, p99 64 |
| 행별 위험 목표 τ=0.03 | 0.08015 | 0.11189 | 26.98 | p50 4, p99 64 |
| **ORACLE 임계** (참 `S_b`) θ=3e-3 | **0.08325** | 0.12298 | 3.12 | p50 1, p99 28 |
| **ORACLE 임계** θ=1e-3 | **0.07139** | 0.10335 | 12.97 | p50 4, p99 64 |
| **ORACLE 임계** θ=3e-4 | **0.05535** | 0.08404 | 34.37 | p50 32, p99 64 |

**결론 1 — 헤드룸은 실재합니다.** 오라클 임계는 같은 평균 예산에서 균등 대비
`m̄=3.12`에서 −12%, `m̄=12.97`에서 −13%, `m̄=34.4`에서 −18%의 오차를 줍니다.

**결론 2 — 그러나 key-side 대리변수는 그 헤드룸을 전혀 회수하지 못합니다.**
시도한 4개 규칙 전부가 동일 평균 예산의 균등 배분보다 **나쁩니다.**

원인은 명확합니다. `M̂_b = exp(z̄_b + 3σ_b)`는 `σ_b`에 대해 **지수**이므로 여유
(slack)가 행마다 자릿수 단위로 다릅니다. **행 *안에서* 순서를 매기는 데는 충분하지만
(그래서 랭킹으로는 훌륭합니다, §4.2 N3), 행 *사이*를 비교하는 절대 눈금으로는
쓸 수 없습니다.** 예산 분포가 p50=1, p99=64로 극단적으로 치우치는 것이 그 증상입니다.

더 근본적으로: **추가 예산이 필요한 행은 곧 추정이 틀린 행인데, 추정기는 자신이
틀렸다는 것을 모릅니다.**

### 5.3 되는 방향 — **per-head 정적 배분** (권장)

per-row가 아니라 per-head로 올리면 상황이 뒤집힙니다. `err_exp8_c3`의 분산 중
**64.6%가 head 사이**의 분산이고 35.4%만 head 내부입니다. 즉 **head가 적응의 올바른
단위**입니다. layer별 평균 오차도 0.057~0.503으로 9배 차이납니다.

per-(layer, head) MSE 곡선 위에서 한계이득 greedy로 배분한 결과 (총예산 동일):

| 총예산 `m̄` | 균등 RMSE | **per-head RMSE** | 개선 | 배분 분포 |
|---|---|---|---|---|
| 2 | 0.21957 | **0.19987** | **−9.0%** | m=1:700, 2:220, 4:67, 8:20, 16:4, 32:13 |
| 4 | 0.20768 | **0.18923** | **−8.9%** | 1:442, 2:313, 4:111, 8:69, 16:51, 32:38 |
| **8** | 0.19653 | **0.18027** | **−8.3%** | 1:290, 2:261, 4:129, 8:106, 16:100, 32:138 |
| 16 | 0.18278 | **0.17221** | −5.8% | 1:148, 2:164, 4:99, 8:97, 16:111, 32:405 |
| 32 | 0.16409 | 0.16409 | 0.0% | 전부 32 (상한) |

최적 배분은 **극단적으로 비균등**합니다: `m̄=8`에서 290개 head가 m=1, 138개 head가
m=32를 받습니다. layer별 평균 m은 L0에서 24.2, L12에서 1.7로 14배 차이납니다.

**이 방식이 옳은 이유:**
- 오프라인 보정 → 런타임 결정 비용 **0**
- head별 m이 고정 → 커널 launch가 ragged가 되지 않음
- RetroInfer가 "unattainable"이라고 쓴 문제(layer/head별 최적 cluster 수)에 대한
  직접적 답

**구현 완료:** `UTAMultiBinConfig.expand_m_table`, `run_multibin_hat_bench.py`의
`UTA+expandhead`. 균등 테이블을 넣으면 균등 경로와 **비트 단위로 동일**함을 검증했습니다.

### 5.4 Latency — adaptive가 실제로 무엇을 물리는가

`bench_adaptive_latency.py`, H100 NVL, B=32, K=32768, Hq/Hkv=32/8, d=128, ρ=5%,
NB=974, 유휴 GPU 단독. `results/adaptive_b32.json`.

**(1) 결정 자체의 비용**

| 단계 | ms |
|---|---|
| bin 모멘트 `z̄_b`, `σ_b²` (양쪽 공통, bmm ×2) | 0.1391 |
| 고정 예산 선택 (topk m) | 0.0977 |
| adaptive 결정만 (share, 비교, count) | 0.1041 |
| adaptive 선택 전체 (결정 + ragged 인덱스 구성) | 0.2640 |
| **adaptive 결정 오버헤드** | **+0.1663** |

**(2) 커널 비용 — padding 폭의 함수**

| padded m | 확장 토큰 | 커널 ms |
|---|---|---|
| 0 | 0 | 0.5466 |
| 8 | 256 | 0.5913 |
| 16 | 512 | 0.6438 |
| 32 | 1,024 | 0.7523 |
| 64 | 2,048 | 0.9626 |

**(3) raggedness의 비용** — 평균 예산은 8인데 배치 최댓값까지 padding해야 합니다:

| 배치 max m | 평균 m | 커널 ms | 고정 m=8 대비 |
|---|---|---|---|
| 8 | 7.98 | 0.5896 | 1.00× |
| 16 | 8.24 | 0.6282 | 1.06× |
| 32 | 8.47 | 0.6982 | 1.18× |
| **64** | **8.93** | **0.8306** | **1.40×** |

§5.2의 측정된 예산 분포는 p99=64이므로 실제로는 마지막 행에 해당합니다.

**총합 (decode step, B=32):**

| 경로 | 모멘트 | 선택 | 커널 | **합계** | 고정 대비 |
|---|---|---|---|---|---|
| 고정 m=8 | 0.139 | 0.098 | 0.591 | **0.828 ms** | 1.00× |
| per-row adaptive (측정된 분포) | 0.139 | 0.264 | 0.831 | **1.234 ms** | **1.49×** |
| per-row adaptive (max m을 16으로 캡) | 0.139 | 0.264 | 0.628 | **1.031 ms** | 1.24× |
| **per-head 정적 (§5.3)** | 0.139 | 0.098 | ~0.591 | **~0.828 ms** | **1.00×** |

**즉 per-row adaptive는 +49% latency를 물고 정확도 이득이 0(또는 음수)입니다.**
per-head 정적 배분은 +0% latency에 −8.3% RMSE입니다. 선택은 명확합니다.

**주의:** 커널의 확장 루프는 `for start in range(0, N_EXP, BLOCK_N)`으로 `N_EXP`가
**모든 program이 공유하는 런타임 스칼라**입니다([triton_expand_decode.py:90](../triton_expand_decode.py#L90)).
따라서 위 raggedness 비용은 *현재 커널*의 값입니다. program별 카운트 배열
(`n = tl.load(Counts + pid)`)로 바꾸면 비용이 max가 아니라 mean을 따라가고, 남는
것은 SM 간 부하 불균형뿐입니다 — 1,024 program / 132 SM이면 평균화됩니다.
**이 커널 수정은 미착수이며, 하면 per-row adaptive의 비용 논거는 약해집니다.**
다만 §5.2에 따르면 그래도 정확도 이득이 없으므로 우선순위는 낮습니다.

### 5.5 다음에 시도할 만한 것 (미측정)

per-row 대리변수가 실패한 원인이 "추정기가 자신의 오류를 모른다"는 것이므로,
**tail 통계가 아니라 셀렉터의 확신도**를 신호로 쓰는 것이 남은 방향입니다.
V5 §5의 E0 진단이 이미 재료를 갖고 있습니다 — HAT 경계 τ의 중앙값이 **0**(무작위
수준)이고 예산의 32%가 동점 그룹에서 임의 충당됩니다. `τ`가 낮은 행 = HAT이 추측한
행 = 확장이 더 필요한 행일 가능성이 큽니다. `τ`, `hat_score_max − τ`,
`hat_tie_frac_of_budget`은 셀렉터가 이미 계산하는 값이라 추가 비용이 없습니다.
**미측정이며, `run_softmax_decomp_diag.py`에 HAT 점수를 넣으면 한 번의 실행으로
판정됩니다.**
