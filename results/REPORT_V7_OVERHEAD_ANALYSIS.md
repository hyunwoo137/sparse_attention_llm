# V7 — 오버헤드 분해: expand의 병목은 무엇인가

H100 NVL · Llama-3.1-8B 형상 (Hq/Hkv = 32/8, d=128) · K=32768 · ρ=5% · m=8 · bf16
`bench_expand_profile.py`, `bench_access_pattern.py` · **유휴 GPU(cuda:1) 단독 실행**

V6는 "sparse가 dense보다 느리다"에서 멈췄습니다. 이 보고서는 **어디서** 느린지를
분해하고, 그 원인이 알고리즘인지 구현인지를 실험으로 가릅니다.

---

## 0. 먼저: `dense`와 batch size B의 관계

`dense`는 full attention이 맞습니다. `B`는 **동시에 처리하는 시퀀스 수**이고,
시퀀스마다 독립된 KV 캐시가 있으므로 B가 커지면 읽을 KV도 그만큼 늘어납니다.

| B | KV 캐시 | dense 시간 | 유효 대역폭 |
|---|---|---|---|
| 1 | 134.2 MB | 0.121 ms | 1.11 TB/s (피크의 28%) |
| 8 | 1,073.7 MB | 0.414 ms | 2.59 TB/s (66%) |
| 32 | 4,295.0 MB | 1.594 ms | **2.69 TB/s (69%)** |

KV가 32배인데 시간은 13배만 늘어납니다 — **B=1에서는 GPU가 놀기 때문**입니다(커널 런치
오버헤드, 병렬성 부족). **따라서 이후 모든 비교는 B=32에서 합니다.** 거기서만 하드웨어가
포화되어 방법 간 차이가 구현 아티팩트가 아닌 실제 비용을 반영합니다.

## 1. Stage 분해 (B=32)

각 stage를 **입력을 미리 만들어 둔 채 단독으로** 측정했습니다. 따라서 한 stage의 비용이
그것을 먹여주는 stage에 오염되지 않습니다.

| stage | ms | 비중 | MB | 달성 GB/s |
|---|---|---|---|---|
| **S1 선택 KV 읽기** | **2.159** | **60.8%** | 824.7 | **382** |
| S8 merge softmax | 0.442 | 12.5% | 63.8 | 144 |
| S6 확장 KV 읽기 | 0.373 | 10.5% | 134.2 | 360 |
| S2 선택 로짓 (bmm) | 0.266 | 7.5% | — | — |
| S3 bin 통계 (bmm ×2) | 0.120 | 3.4% | 127.7 | **1,063** |
| S4 랭킹 + topk | 0.111 | 3.1% | — | — |
| S7 확장 로짓 (bmm) | 0.042 | 1.2% | — | — |
| S5 확장 인덱스 구성 | 0.036 | 1.0% | — | — |
| **합계** | **3.550** | | | |

### 두 가지가 바로 읽힙니다

**(1) 병목은 우리 방법이 추가한 부분이 아닙니다.** S1(60.8%)은 **모든 sparse top-k 방법이
공통으로 내는 비용**입니다 — HAT도, vAttention도 똑같이 냅니다. expand가 추가한 것은
S3+S4+S5+S6+S7 = **0.682 ms, 전체의 19.2%**뿐입니다.

**(2) bin 통계는 이미 빠릅니다.** S3이 1,063 GB/s로 다른 읽기(382 GB/s)의 2.8배입니다.
k̄_b/Var_b가 **연속 배치**된 텐서라서입니다. 같은 GPU, 같은 시각, 다른 접근 형태 —
이 대비가 다음 절의 실험을 부릅니다.

## 2. 원인 규명 — granularity가 아니라 **커널**입니다

### 2.1 가설 1: 접근 단위가 작아서인가?  → **기각**

총 바이트를 고정하고 **접근 블록 크기만** 바꿔 측정했습니다.

| 접근 형태 | ms | GB/s | 스트림 대비 |
|---|---|---|---|
| 랜덤 블록 1행 | 1.121 | 383.2 | 0.14× |
| 랜덤 블록 8행 | 1.116 | 384.6 | 0.14× |
| 랜덤 블록 32행 | 1.116 | 384.6 | 0.14× |
| 랜덤 블록 128행 | 1.051 | 408.4 | 0.14× |
| 랜덤 블록 512행 | 1.052 | 408.3 | 0.14× |
| **연속 스트림 (참조)** | **0.152** | **2,825.8** | 1.00× |

블록을 512배 키워도 383 → 408 GB/s로 **사실상 평평합니다.** 각 행이 이미 128×2 = 256바이트
(캐시라인 2개)라 접근 단위는 애초에 충분히 컸던 것입니다.

**따라서 bin 크기를 키우는 것은 지렛대가 아닙니다** — V6 §5.3에서 "접근 단위를 키우는 것이
유일한 지렛대"라고 쓴 것은 이 측정으로 반증됐습니다.

### 2.2 가설 2: 흩어진 접근이라서인가?  → **기각**

같은 `index_select`에 **순차 인덱스**를 주면 어떻게 되는지가 결정적입니다.

| case | ms | payload GB/s | 총 트래픽 GB/s |
|---|---|---|---|
| index_select, **랜덤** 인덱스 | 1.122 | 382.8 | 765.7 |
| index_select, **순차** 인덱스 | **1.122** | 382.8 | 765.7 |
| narrow + clone (순수 복사) | **0.251** | 1,712.1 | **3,424.2** |
| narrow + sum (읽기만) | 0.153 | 2,810.2 | 2,810.2 |

**랜덤과 순차가 소수점까지 같습니다.** 메모리 시스템이 한계였다면 순차가 훨씬 빨라야 합니다.

### 2.3 가설 3: gather 구현이 나빠서인가?  → **부분적으로만**

PyTorch가 제공하는 gather 경로를 전부 재봤습니다. 원소 수가 문제라면 행을 int64로
재해석(128개 → 32개 원소)했을 때 빨라져야 합니다.

| 구현 | ms | 트래픽 GB/s |
|---|---|---|
| index_select, bf16 (D=128 원소) | 1.122 | 765.1 |
| index_select, int32 view (D=64) | 1.121 | 766.1 |
| index_select, int64 view (D=32) | 1.121 | 765.9 |
| advanced indexing `src[idx]` | 1.120 | 766.8 |
| `torch.embedding(src, idx)` | 1.121 | 766.2 |

**전부 동일합니다.** 구현을 바꿔도, 벡터화해도 766 GB/s 천장에 걸립니다.

### 2.4 진짜 원인: **행이 너무 작습니다**

총 이동량을 고정하고 **gather 단위(한 인덱스가 가리키는 바이트 수)**만 키웠습니다.

| gather 단위 | 행 크기 | ms | 트래픽 GB/s |
|---|---|---|---|
| blk=1 (토큰 1개) | 256 B | 1.122 | 766 |
| **blk=4** | 1 KB | **0.291** | **2,949** |
| blk=16 | 4 KB | 0.273 | 3,144 |
| blk=64 | 16 KB | 0.275 | 3,124 |
| blk=1024 | 256 KB | 0.255 | 3,362 |
| 연속 복사 (참조) | — | 0.251 | 3,428 |

**토큰 4개만 묶어도 3.85배, 16개면 사실상 연속 복사 수준입니다.**

원인이 이제 분명합니다 — 토큰 한 행은 128 × 2B = **256바이트뿐이고, 인덱스 하나당
치러야 하는 주소 계산·런타임 간접 참조 비용이 그 256바이트에 상각되지 않습니다.**
행이 1 KB를 넘으면 상각되어 사라집니다. 접근이 흩어졌는지 여부는 무관합니다(§2.2).

## 3. 우리 방법의 오버헤드 — 절반은 **지금 당장** 해결됩니다

### 3.1 확장 bin은 이미 연속입니다

**확장 bin은 인접 인덱스 32토큰 런 = 8 KB**입니다. 즉 §2.4가 말하는 "충분히 큰 행"을
**우리는 이미 갖고 있습니다.** 토큰 단위로 gather할 이유가 없고, bin 단위로 한 번에
읽으면 됩니다.

| S6 확장 KV 읽기 (134.2 MB) | ms | GB/s |
|---|---|---|
| 토큰 단위 gather (기존) | 0.399 | 673 |
| **bin 단위 gather (blk=32)** | **0.108** | **2,476** |

**3.68배, 결과는 비트 단위로 동일**(`torch.equal` = True). 커스텀 커널 없이 reshape
하나로 얻어집니다. 벤치마크에 반영한 결과 `expand_gather`가
**3.411 → 3.127 ms (2.14× → 1.96× dense)**로 내려갔습니다.

여기서 주목할 점 — **인접 분할은 원래 순환을 피하려고 고른 것**이었습니다(로짓 없이
bin 멤버십을 정할 수 있으므로). 그 선택이 **메모리 접근 효율까지 같이 준 것**입니다.
V4의 랜덤 분할이나 score bin은 이 성질이 없습니다. 흩어진 토큰을 모아야 하니까요.

### 3.2 남은 우리 몫

| stage | ms | 성격 |
|---|---|---|
| S3 bin 통계 | 0.120 | 연속 읽기, 이미 1,063 GB/s |
| S4 랭킹 + topk | 0.111 | 순수 연산 (`sorted=False`로 0.069까지) |
| S5 인덱스 구성 | 0.036 | bin 단위 gather로 대부분 소멸 |
| S6 확장 KV 읽기 | **0.108** | 0.373에서 개선 |
| S7 확장 로짓 | 0.042 | bmm |
| **우리 몫 합계** | **0.417** | 전체(3.284)의 **12.7%** |

수정 전 0.682 ms(19.2%)에서 **0.417 ms(12.7%)**로 내려갔습니다. 나머지 87%는
**모든 sparse top-k 방법이 공통으로 내는 비용**입니다.

## 4. 공통 병목(S1)을 어떻게 풀 것인가

S1이 느린 이유는 §2.4와 같습니다 — HAT top-k가 **개별 토큰 인덱스**를 돌려주므로
행이 256바이트입니다. 셀렉터가 **블록 단위로 고르면** 그대로 해소됩니다.

| S1, 같은 토큰 예산(1,638개) | ms | GB/s |
|---|---|---|
| 토큰 단위 선택 (현재) | 2.233 | 769 |
| **8토큰 블록 선택** | **0.526** | **3,265** |
| 32토큰 블록 선택 | 0.541 | 3,174 |

**4.24배.** 다만 이건 §3.1과 성격이 다릅니다 — **알고리즘 변경**입니다. HAT이 블록
단위로 점수를 매기고 뽑아야 하며, **정확도에 영향이 있는지는 측정되지 않았습니다.**
블록 8토큰이면 선택 해상도가 8배 거칠어지므로, E0에서 본 "무거운 토큰이 흩어져 있다"는
성질과 충돌할 수 있습니다.

### 4.1 갱신된 투영

| 구성 | 합계 ms | dense(1.594) 대비 |
|---|---|---|
| 현재 (토큰 gather) | 3.550 | 2.23× |
| **+ bin 단위 확장 읽기** (§3.1, 적용됨) | **3.284** | **2.06×** |
| + 8토큰 블록 셀렉터 (§4, 미검증) | 1.651 | **1.04×** |
| + merge/통계까지 fused | ~1.2 | ~0.75× |

**블록 셀렉터까지 가면 dense와 대등**해지고, fused 커널이 그 아래를 엽니다.
1행은 이미 확보했고, 2행은 정확도 검증이 필요하며, 3행은 커널 작업입니다.

### 4.2 우선순위

| 순위 | 대상 | 절감 | 성격 | 상태 |
|---|---|---|---|---|
| **1** | 확장 bin을 blk 단위로 읽기 | 0.27 ms | reshape만 | **완료** |
| 2 | 셀렉터를 블록 단위로 (8토큰) | 1.71 ms | **알고리즘 변경, 정확도 미검증** | 제안 |
| 3 | merge softmax 융합 | ≤0.44 ms | 커널 | 미착수 |
| 4 | S4 `sorted=False` | 0.04 ms | 한 줄 | 미착수 |
| — | ~~bin 크기 확대로 대역폭 개선~~ | 0 | §2.1에서 반증 | 폐기 |

## 5. 상대 비교 (같은 밀도 ρ=5%, query head·layer당)

| | 토큰 | KB | 비고 |
|---|---|---|---|
| ours 선택 | 1,636 | 837.6 | |
| ours 확장 (m=8) | 256 | 131.1 | 연속 32토큰 블록 8개 |
| ours bin 통계 ÷ g=4 | — | 93.3 | query 무관, GQA 그룹 공유 |
| **ours 합계** | **1,892** | **1,062.0** | |
| vAtt selector (ρ/2) | 817 | 418.3 | |
| vAtt 샘플 (ρ/2) | 819 | 419.3 | query마다 다른 개별 랜덤 |
| **vAtt 합계** | **1,636** | **837.6** | |

**ours / vAttention = 1.27배 바이트.** 정확도는 85.35 vs 68.70 (+16.65%p).
정직한 서술은 **"같은 밀도에서 27% 더 읽고 16.65%p 더 정확하다"**입니다.

wall-clock으로도 vAttention은 dense보다 느립니다(B=32에서 2.815 ms, **1.77×**).
vAttention에는 추가로 **두 단계 순차 의존**(base 샘플의 std가 나와야 adaptive 예산 결정)과
**행마다 가변인 예산**(커널에서 ragged)이 있습니다. 이 구조적 비용은 §3의 fused 커널로도
사라지지 않습니다.

## 7. 한계

- 투영(§3)은 **측정이 아닙니다.** fused 커널은 미작성입니다.
- 모든 수치는 **합성 텐서**입니다. 실제 KV 분포·페이지 배치가 gather 성능을 바꿀 수 있습니다.
- `index_select`가 최적 gather라는 보장이 없듯, **2,810 GB/s가 달성 가능한 상한이라는
  보장도 없습니다.** 읽기 전용 reduction으로 잰 값입니다.
- prefill 비용과 bin 통계 구축 비용은 제외했습니다(생성 전체에 상각).
